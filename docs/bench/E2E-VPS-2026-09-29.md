# bunvex end to end vs Convex, minivex and raw Bun + Postgres (VPS, 29 Sep 2026)

> **Superseded** by [E2E-VPS-2026-10-05](E2E-VPS-2026-10-05.md): bunvex is slower today than here (see
> [RERUN-2026-10-04](RERUN-2026-10-04.md)). Kept as the record of 29 Sep; do not cite these numbers as current.

Same box for everything: Hostinger KVM2 (2 vCPU AMD EPYC 9354P, 8 GB, real fsync), k6 and the fan-out
generator co-located (they compete for CPU with every server). Harness: `~/sandbox/convex-bench`
(`scripts/run-suite.sh`, `load/k6/bench.js`, `load/ws/fanout.mjs`), unchanged API for bunvex (Convex's
`/api/{query,mutation,action}` shape). One server at a time. One run per point.

| target | how it ran |
|---|---|
| Convex | self-hosted, Docker `network_mode: host`, profile `tuned`, Postgres 17 |
| minivex | 1 process, `CHANGELOG=local`, Postgres 17 |
| Bun + PG | raw handlers, 2 workers, autocommit (a weaker contract: no OCC, no reactivity) |
| bunvex | 1 process (`src/server.ts`), OCC + group commit + query cache; storages: memory+log, `bun:sqlite`, Postgres 17 (**the same instance Convex used**), MySQL 8.4 (`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`), MongoDB 8.3 standalone (commit marker with `j:true`, STORAGE-01) |

## What this shows and what it does not

- The engine core, not the language, decides: a TypeScript engine beats Convex's Rust backend on every
  scenario except the single hot key, on every storage, including the very same Postgres.
- The memory storage is bounded by RAM and has no retention / snapshot / log replay yet. SQLite, Postgres
  and MySQL are durable stores with full history.
- Cached reads (~7–9k/s) are capped by HTTP + k6 on 2 vCPU for everyone.
- **Weak spot: one hot key.** Group commit + OCC lets only the first increment of a key per group pass;
  the rest retry a whole flush later — ~1 000/s on memory, ~100–200/s on remote storages, with retry
  exhaustion. Next step: pipelined commit (mutations read the applied-but-not-yet-durable state; they
  still answer only after their group and every earlier group is durable; queries keep reading durable
  state only).
- Not yet built: retention/GC, restart recovery for the memory log, schema validation, auth, scheduler,
  file storage, search. The comparison is on the benchmark's surface only.

## MongoDB (added the same day, after STORAGE-01)

All five drivers pass the conformance suite K1–K7 on the VPS (`bench/conformance.ts`, 8 SIGKILLs per
driver); each property was sabotaged once and went red. MongoDB is the slowest on uncached reads (997/s):
a range read is two round trips (latest index entries, then one aggregation for the documents) and each
query goes through MongoDB's query planner; it still does 3.3× Convex. Durable writes (4 436/s) are in
the range of the SQL stores: the commit marker costs one extra journaled round trip per GROUP, not per
commit.
