# bunvex end to end vs Convex (VPS, 5 Oct 2026)

The numbers bunvex publishes (README, site), measured again on main at `9f588081` (#413), after the
regressions found by the [4 Oct rerun](RERUN-2026-10-04.md) and their fixes (#407, #410–#413). It replaces
[E2E-VPS-2026-09-29](E2E-VPS-2026-09-29.md) as the cited report: bunvex is slower than on 29 Sep, and the
gaps to Convex below are smaller than the ones published then.

Same box and harness as 29 Sep: Hostinger KVM2 (2 vCPU AMD EPYC 9354P, 8 GB, real fsync), k6 and the
fan-out generator on the box (they compete for CPU with every server), `convex-bench`
(`scripts/run-suite.sh`, `load/k6/bench.js`, `load/ws/fanout.mjs`). One server at a time, one run per point,
20 s per point.

| target | how it ran |
|---|---|
| Convex | self-hosted, Docker `network_mode: host`, profile `tuned`, Postgres 17; **run again today** for HTTP |
| bunvex | 1 process (`bench/server.ts`, the write throughput limit lifted), main at `9f588081`; storages: memory+log, `bun:sqlite`, Postgres 17 (**the same instance Convex used**), MySQL 8.4 (`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`), MongoDB 8 (single-node replica set) |

minivex and raw Bun + Postgres were not run again; their 29 Sep numbers are in the old report.

## Fan-out (WebSocket, 20 messages to N subscribers of one query)

bunvex now splays wide invalidations as Convex does (STUDY-08: more than 200 subscribers, notifications
spread over ~N × 5 ms), so with the shipped settings both skip intermediate values alike. The comparison is
therefore made with the splay off on both: Convex's `raw` profile, bunvex's
`SUBSCRIPTION_INVALIDATION_DELAY_MULTIPLIER=0`. Convex's fan-out was not run again: its column is from
29 Sep (`20260929-0103-vps-convex-fanout-raw`).

## What this shows and what it does not

- bunvex is still ahead of Convex on every scenario on the same Postgres, but by less than published on
  29 Sep: about 1 300 commits of features (function logs, usage metering, value formats, CORS, …) made each
  request cost more. #407 and #411–#413 won part of it back; the rest is spread over per-request layers.
- The hot key (one document incremented by every client) fails on both, with retries exhausted.
- Cached reads (~6k/s) are capped by HTTP + k6 on 2 vCPU.
- The comparison covers the benchmark's surface only.
