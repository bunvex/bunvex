# The bench rerun of 4–5 Oct 2026: every scenario, compared with 29 Sep

Everything measured on 29 Sep ([E2E-VPS](E2E-VPS-2026-09-29.md), [E2E-MAC](E2E-MAC-2026-09-29.md),
[ENGINE-00](ENGINE-00-microbench.md)) and the studies' benches, run again on main at `3dac9c6a` (#397), about
1 300 commits later. Same boxes, same harness (`convex-bench`), one server at a time:
- **VPS:** Hostinger KVM2, 2 vCPU, real fsync; Postgres 17, MySQL 8.4, MongoDB 8 in Docker; k6 and the
  fan-out generator on the box.
- **Mac:** M1 Pro, 8 cores; native stores (`scripts/mac-stores.sh`). The other Claude sessions paused their
  tests during the run.

## What the harness needed

- **The write throughput limit** (4 MiB/s, STUDY-78) refused the seed's 2 000-document mutations (429
  `TooManyWrites`) and would cap the insert scenario. `bench/server.ts` now lifts it unless
  `MAX_BYTES_WRITTEN_PER_SECOND` is set, the seed retries a 429, and the Mac suite runs insert once more at
  Convex's limit (below).
- **MongoDB must be a replica set** (the driver needs transactions): `mac-stores.sh` starts a single-node
  `rs0`; the VPS container was recreated with `--replSet rs0`.
- **The VPS copy of `convex-bench`** still had the old bunvex WebSocket protocol in `fanout.mjs`; it now
  uses the official client, as the Mac copy.
- **ENGINE-00 M2/M3** committed at snapshot 0, which the write log's retention now refuses on a fast store:
  they commit at the latest snapshot.

## Findings

1. **HTTP throughput fell 2–4× on every store**, CPU-bound in the request path (the same rate at 8, 32 and
   128 VUs; the stores and the engine core did not slow down, see the microbenchmarks).
2. **Cached queries fell at one merge:** a commit timeline on the VPS (memory store, 32 VUs) measured
   5 774 req/s before `859bf981` (round 287–299, the HTTP API's value formats) and 2 530 after. A CPU
   profile put 52 % in formatting the answer: a `Buffer` per key comparison, floats through the general
   layout, and the same cached result parsed and rewritten for every caller.
3. **Writes fell gradually** (insert −40 % from 30 Sep to 3 Oct, no single step): layers added per request.
   The largest: sort-key encoding (11 %, the new encoder of 29 Sep evening allocates per string), the request
   body cap's stream (4 %), then the function log, usage metering, client-version and CORS layers.
4. **#407 fixes the measured hot spots** (same output; property tests and sabotage in the PR): cached
   queries ×2.8–3.3 on the VPS, uncached +23–95 %, inserts +10–59 %, actions +7–19 % (increment on MongoDB
   −4 %, within noise). What remains below 29 Sep is spread over per-request layers.
5. **Fan-out is not a regression in behaviour:** bunvex now splays wide invalidations as Convex does (more
   than 200 subscribers: notifications spread over ~N × 5 ms), so late subscribers skip intermediate values
   — the same numbers as Convex's default profile on 29 Sep. With the splay off (Convex's `raw` profile),
   every message arrives, but at 10 000 subscribers p99 is 3–4× that of 29 Sep: cost per delivery, mostly the
   per-session cache-hit log (#328, as Convex) and the socket sends. Not fixed here.
6. **The write limit costs nothing in this suite:** inserts at 4 MiB/s run as fast as with the limit lifted.
